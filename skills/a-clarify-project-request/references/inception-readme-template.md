# Inception

This directory contains the information used to understand, clarify, and establish a new software project before detailed requirements, architecture, implementation, or testing begin.

The inception stage separates original evidence from the documents generated by the workflow.

## Contents

### `sources/`

Contains the original, unrefined information received about the project.

Examples include:

* Informal project requests.
* Emails from requesters or stakeholders.
* Meeting notes.
* Interview transcripts.
* Existing-system descriptions.
* Reference documents supplied by stakeholders.

Files in `sources/` are evidence. They must not be rewritten, replaced with summaries, or modified to incorporate later interpretations.

See [`sources/README.md`](sources/README.md) for the source-preservation rules.

### `clarified_project_request.md`

Contains the clarified interpretation of the original project request.

It records:

* The initial understanding of the request.
* The problem or opportunity.
* The intended outcome.
* The expected users or beneficiaries.
* The broad initial project boundary.
* Project-level constraints, dependencies, and risks.
* Clarification questions.
* Stakeholder answers and their impact.
* Contradictions or unresolved uncertainty.
* The formal human readiness decision.

This document answers:

> Is the original project request sufficiently clear to form a Project Context?

It is generated and maintained by the Project Request Clarification workflow.

It does not define detailed requirements, user stories, architecture, implementation tasks, or test cases.

### `project_context.md`

Contains the approved general foundation for the project and its first release.

It describes:

* Why the project exists.
* Who the project serves.
* The general problem and intended outcome.
* The broad software boundary for the first release.
* Important constraints and risks.
* Responsibilities and approval roles.
* General success conditions.

This document answers:

> What general context should guide the definition of the first release?

It is generated by the Project Context Formation workflow after `clarified_project_request.md` has been approved as ready.

It does not contain detailed requirements, user stories, acceptance criteria, architecture decisions, or implementation details.

## Artifact Relationship

The inception artifacts are used in this order:

```text
Original sources
    ↓
clarified_project_request.md
    ↓
project_context.md
    ↓
../01_requirements/product_requirements.md
```

Each artifact has a different purpose:

* `sources/` preserves what was originally provided.
* `clarified_project_request.md` records the clarified interpretation.
* `project_context.md` establishes the approved general project foundation.
* `product_requirements.md` defines detailed requirements and user stories.

Do not treat these artifacts as interchangeable or copy one artifact wholesale into the next.

## Structural Responsibility

This directory and its explanatory README files are created by the project template.

Workflow skills may verify that the structure exists, but they must not silently overwrite structural documentation.

Missing structural files should be reported and restored only with explicit user authorization.

The operational status of the workflow is tracked separately in:

```text
sdlc_docs/trace_workflow.md
```
